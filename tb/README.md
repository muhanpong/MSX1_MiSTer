# ch2 word-latch testbench

Counts the `CMD_ACTIVE` commands the SDRAM controller issues for a given ch2
(CPU) access pattern, with and without the read word latch, and checks every
returned byte against a behavioural memory model.

    apt-get install verilator     # 5.x
    make          # runs both configurations
    make clean

`sdram_sim.sv` is generated by `mkshim.py` from `../rtl/peripheral/sdram.sv`.
The shim only splits the bidirectional `SDRAM_DQ` into `_o`/`_oe`/`_i` and
hoists `state` to module scope; Verilator supports neither procedural tristate
on an `inout` nor the mixed blocking/non-blocking assignment the in-block
declaration creates. The latch logic under test is unchanged.

## Results (Verilator 5.020)

| pattern                         | latch off | latch on |
|---------------------------------|-----------|----------|
| A sequential fetch, 32 bytes    |  32       | 16       |
| B fetch + stack interleaved     |  96       | 64       |
| C LDIR-like copy, 32 bytes      |  64       | 48       |
| D random reads in 4 kB          |  32       | 32       |
| **total**                       | **224**   | **160**  |

160 reads, 64 writes; 64 reads answered from the latch = 40%.

## Line-variant model

The same trace is also fed to offline models of configurations that are NOT
implemented, so their value can be judged before any burst-mode work:

| variant                          | hits | rate |
|----------------------------------|------|------|
| 1 word, blanket invalidation     | 48   | 30%  |
| 2 words, blanket                 | 56   | 35%  |
| 4 words, blanket                 | 60   | 37%  |
| 2 lines x 1 word, blanket        | 48   | 30%  |
| **1 word + address-compare**     | 64   | 40%  |
| 2 words + address-compare        | 80   | 50%  |
| 4 words + address-compare        | 88   | 55%  |

The self-check line ties the model to the DUT: with the latch enabled the
controller must issue exactly one access per write plus one per read the
1-word address-compare model called a miss. It holds in both configurations,
so the unimplemented rows are trustworthy on this trace.

Caveat: the four patterns are synthetic and weighted equally. The ratios
between variants carry more weight than the absolute percentages.

## Guard interaction (`make guard`)

`guard_tb.sv` puts the real `sdram.sv` next to a transcription of `msx.sv`'s
fast-SDRAM-read bus guard (P3 closed loop + P4 hit path) and checks, on every
clk21m edge of every read, that `guard_open` is never high while `ch2_dout` is
not yet the requested byte. clk21m is derived from clk_sdram at /4 with the
60-degree lag `pll.v` applies.

| read                          | P4=0 (before) | P4=1 (after) |
|-------------------------------|---------------|--------------|
| miss                          | clk21m 2, closed loop | clk21m 2, closed loop |
| hit (paired byte)             | **clk21m 15, watchdog** | **clk21m 1, hit path** |
| hit after write to that word  | miss, clk21m 2 | miss, clk21m 2 |
| hit after unrelated write     | clk21m 15, watchdog | clk21m 1, hit path |

Neither configuration ever opened the guard on stale data. Without the
`msx.sv` change every latch hit sits on the 15-cycle watchdog, which is the
stall the P4 change exists to remove. The guard block in `guard_tb.sv` is a
copy; keep it in step with `msx.sv`.
