# ch2 read-cache testbenches

`make` runs three things against the real `rtl/peripheral/sdram.sv`:

    make nolatch   # CACHE_LINES=0   (original behaviour)
    make latch     # CACHE_LINES=8192
    make guard     # guard/cache interaction, P4 off and on
    make clean

`sdram_sim.sv` is generated by `mkshim.py` from the repo file. The shim only
splits the bidirectional `SDRAM_DQ` into `_o`/`_oe`/`_i` and hoists `state` to
module scope; Verilator supports neither procedural tristate on an `inout` nor
the mixed blocking/non-blocking assignment the in-block declaration creates.
The cache logic under test is unchanged.

## sdram_tb — access counts (Verilator 5.020)

Every returned byte is checked against a behavioural memory model.

| pattern                              | cache off | 8192 lines |
|--------------------------------------|-----------|------------|
| A sequential fetch, 32 bytes         |  32       |  16        |
| B fetch + stack interleaved          |  96       |  64        |
| C LDIR-like copy, 32 bytes           |  64       |  48        |
| D random reads in 4 kB               |  32       |  31        |
| E main loop x8 (code+stack+data)     | 576       | 124        |
| **total**                            | **800**   | **283**    |

672 reads, 128 writes. 517 reads answered from the cache = **76%**; the
1-line word latch would have hit 320 = 47% on the same trace. E is the case
a cache exists for: the same code block, stack and data touched every
iteration. What still misses there is the stack, because each PUSH
invalidates its line by index and the POP has to refetch.

**F — write/read race sweep.** For 16 relative offsets, a ch1 write to X and a
ch2 read of X are fired that many clk cycles apart, chosen to land the
invalidate on or next to the cache lookup edge. A later read of X must return
the written value. 0 stale in both configurations. This is the direct test of
the read-during-write hazard guard (`c_hazard`).

**Self-check.** An offline model with the DUT's exact geometry and its
invalidate-by-index rule predicts the access count; the DUT must match it
exactly (F excluded, since cross-channel ordering is unspecified). A
read-during-write hazard in the DUT would show as a surplus access here.
Both configurations match.

## guard_tb — guard interaction

The real `sdram.sv` next to a transcription of `msx.sv`'s fast-SDRAM-read bus
guard (P3 closed loop + P4 hit path), checking on every clk21m edge of every
read that `guard_open` is never high while `ch2_dout` is not yet the requested
byte. clk21m is clk_sdram/4 with the 60-degree lag `pll.v` applies.

| read                          | P4=0 (before)           | P4=1 (after)          |
|-------------------------------|-------------------------|-----------------------|
| miss                          | clk21m 2, closed loop   | clk21m 2, closed loop |
| hit                           | **clk21m 15, watchdog** | **clk21m 1, hit path**|
| hit after write to that word  | miss, clk21m 2          | miss, clk21m 2        |
| hit after unrelated write     | clk21m 15, watchdog     | clk21m 1, hit path    |

No stale-data violation in either configuration. The cache's one-cycle
(clk_sdram) lookup did not move the hit release off clk21m 1. The guard block
in `guard_tb.sv` is a copy of `msx.sv`; keep them in step.

Caveat: the patterns are synthetic. Ratios between variants carry more weight
than absolute percentages; the P5 overlay rows give the real-workload figure.
