# PC 트랩 오버레이 — 크래시가 어디서 났는지 보는 진단 빌드

`MOONSOUND_DIAG` 매크로 뒤에 있다. `MSX1.qsf` 의 그 줄을 주석 처리하면 통째로 사라진다.
정식 빌드에는 들어가지 않는다.

## 왜 만들었나

Hi no Tori 60Hz 패치 롬이 3.58 에서 **확률적으로** 죽는다(맵 로드 중, 좌하단 잡음 + 리부트).
롬 쪽 블랙박스는 리셋 후 BIOS 가 VRAM 을 지워 계속 헛돌았고, 크래시가 확률적이라
시행당 정보량이 낮았다. **코어가 직접 잡는 게 정공법이다.**

## 무엇을 잡는가

핵심은 트랩 조건이다. Konami 매퍼 게임은 4000-BFFF 에서 실행되지만 **BIOS 를 page 0 에서
수시로 호출**하므로 "PC 가 카트 창 밖으로 나갔다" 는 정상이다. 그래서 크래시-리부트의
서명인 **`PC == 0000` 에서의 opcode fetch** 를 잡는다.

그 순간 다음을 **고정**한다(sticky — 첫 사망이 이기므로 뒤따르는 리부트 루프가 못 덮는다):

| 신호 | 내용 |
|---|---|
| `dbg_trap_from` | 0000 으로 뛰기 **직전** opcode fetch 의 PC ← **사망 지점** |
| `dbg_trap_prev` | 그 하나 전 |
| `dbg_trap_sp` | 그때의 SP (`t80_reg[63:48]`, `T80.vhd:259` 레이아웃) |
| `dbg_trap_b10` | Konami 뱅크 `{b1,b0}` 스냅샷 |
| `dbg_trap_b32` | Konami 뱅크 `{b3,b2}` 스냅샷 |
| `dbg_trap_cnt` | `{PC==0000 발생 횟수, 살아있는 bank0}` — 확률 측정용 |

**뱅크는 `konami_scc` 를 건드리지 않고 버스에서 미러링한다**(5000/7000/9000/B000 쓰기를 스누핑).
매퍼에 손대지 않으므로 관찰자 효과가 없고, 파일도 두 개 덜 건드린다.

## 화면에서 읽는 법

OSD 의 **`Debug overlay` 를 On** 으로. 좌상단 패널이 뜬다(`PW=66`, `PH=154`).
각 행은 8px 높이, 16비트를 **4px/비트, MSB 왼쪽**의 막대로 그린다(기존 PC 행들과 같은 형식).

기존 13행 아래에 6행이 추가된다:

    y 104-111  밝은 빨강   dbg_trap_from   ← 사망 지점
    y 112-119  어두운 빨강 dbg_trap_prev
    y 120-127  주황        dbg_trap_sp
    y 128-135  청록        banks {b1,b0}
    y 136-143  어두운 청록 banks {b3,b2}
    y 144-153  흰색        {사망 횟수, 현재 bank0}

전부 0 이면 아직 `PC==0000` 이 한 번도 안 났다는 뜻이다(halt 로 죽었다면 기존
**freeze detector 행**(y 48-55)의 `noM1` 흰 칸이 켜진다).

## 판독 요령

- `dbg_trap_from` 이 **4000-BFFF 안**이면 카트 코드가 스스로 0 으로 뛴 것 → 롬 로직/스택.
- **page 0/RAM** 이면 BIOS 나 RAM 루틴에서 튄 것.
- 뱅크 스냅샷이 게임이 의도한 값과 다르면 **매퍼 경로**를 의심할 근거가 된다.
- `SP` 가 스택 영역 밖이면 스택 폭주.
- 사망 횟수는 확률적 현상의 **빈도 측정**에 그대로 쓴다(시행마다 리셋 없이 누적).

## ★1차 실기 결과 (2026-09-01) 와 그에 따른 수정

첫 캡처(`MSX1_20260901a_pctrap`, m55-unified 크래시)에서 두 가지가 드러났다.

1. **`trap_from` / `trap_prev` 가 전부 0** = `PC == 0000` 이 한 번도 안 났다.
   **이 크래시는 0번지로 뛰는 리부트가 아니라 정지(halt/stall)** 다.
   → 트랩을 **halt 검출기에도** 걸었다. `dbg_cpu_nom1`(약 760us 동안 opcode fetch 없음,
   sticky)의 상승 엣지에서 같은 포렌식을 얼린다. 둘 중 먼저 걸리는 쪽이 이긴다.
2. **reg-probe 패널(Zanac 조사 잔재)이 `v_cnt 120..151` 을 덮어썼다.** 그 패널이
   트랩 행보다 **나중에** 그려져 SP·뱅크 두 행·카운터 행을 조용히 지웠다(폭이 48 단위라
   64 단위 비트 스트립보다 좁게 보이는 것이 그 증거였다).
   → 그 패널을 **오른쪽으로 옮겼다**(`PROBE_X0 = 80`, 즉 `h_cnt 80..127`).
   컴파일 제외가 아니라 이동이라 **두 진단을 동시에 볼 수 있다**. 메인 패널은 `h_cnt < 66`
   이므로 겹치지 않는다.

★교훈: **오버레이에 행을 추가할 때는 뒤에 그려지는 다른 패널과의 좌표 충돌을 먼저 확인할 것.**
`in_panel` 블록 뒤에 독립적으로 그리는 것이 최소 두 개(reg-probe, pause 심벌) 있다.

## 주의

- 트랩은 **sticky** 다. 다시 재려면 코어를 리셋해야 한다(OSD Reset).
- 오버레이는 `en`(= OSD `Debug overlay`)에 게이팅된다. 끄면 아무 비용도 없다.
- pause 심벌과 달리 이 패널은 `en` 게이트 안에 있다.
