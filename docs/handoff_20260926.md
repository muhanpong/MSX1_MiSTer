# Handoff 2026-09-26 — pack builder, MSX-MIDI, SRAM save path, fullsys

Branch `nextz80`, thirteen commits from 56cac78 to 71b283a. Everything below is
pushed.

## 1. What is finished and measured

**The pack builder page** (`tools/CreateMSXpack/packbuilder.html`, published at
`muhanpong.github.io/MiSTer/packbuilder.html`) reads collection `.zip` and `.gz`
archives directly, synthesizes the turbo R WD2793 disk ROM in the browser, and
shows which ROM each pack is waiting on, sorted by how many machines it blocks.
Output still matches `createMSXpack.py` byte for byte on all 86 packs.

**Several SHA-1s per pack entry.** An entry may list more than one `<SHA1>`; the
first one the store has wins. `CART_FW_EN` and `CART_FW_JP` now also accept the
MegaFlashROM image openMSX pins, because the Nextor 2.1.4 image the packs name is
not published anywhere and cannot be built from the open Nextor source — it also
carries Manuel Pazos's cartridge firmware. The `_2slot` packs deliberately do not
accept it.

**MSX-MIDI transmit, against openMSX.** `tools/midi_stream/run_compare.sh` drives
both implementations with the same register sequence (openMSX's `ioports`
debuggable, no MSX-side software) and diffs what comes off the wire. 31 real songs,
963,241 wire bytes, every byte identical; our transmitter measures 31,262 baud,
687 cycles per bit, 0.04 per cent off nominal.

**MSX-MIDI as a cartridge.** `dev_midi` takes an `external` input. The cartridge
form answers E2h alone until told otherwise — bit 7 disables, bit 0 limits it to
E0h-E1h — and reset leaves it at 81h, so a machine that never writes E2h never sees
it. That is what lets MIDI go in a machine that is not an FS-A1GT. `DEV_MIDI_EXT` /
pack type `MIDI_EXT`. Verified against openMSX's own external MSX-MIDI on an
FS-A1WX: 3,353 bytes identical.

**The Panasonic 3-3 pack and load path** — NOT the mapper's runtime behaviour.
`tools/panasonic33/` builds the ST/GT packs that use it (the shipped packs leave 3-3
empty). What the whole-machine bench established, and it is less than the first
version of this document claimed:

| | FS-A1ST | FS-A1GT |
|---|---|---|
| `lookup_SRAM[3]` | 16 kB | 32 kB |
| slot_layout entries | 16 of 64 | 16 of 64 |
| `.sav` bytes into SRAM | all match | all match |

Those three happen before the CPU runs, which is why they survive the correction
below. **The mapper answering CPU accesses has not been measured at all.** The bench
read only the first 2 MB of each pack -- `PACKSZ` was `1 << 21`, the ST pack is
2,491,136 bytes and the GT 4,588,304, and the loader stopped at the buffer without
saying so; the log line reads `pack: 2097152 bytes` and that is the tell. Everything
past the cut was lost, including all four DEVICE records, KBD_LAYOUT and CONFIG.
Without RESET_STATUS port F4 reads FF, the BIOS takes its CPU-switch branch before
RAM is mapped, and the machine ends up looping through RST 38 -- eight distinct PCs
in 400 ms. So every CPU-side number from those runs, including the zero writes during
the `.sav` load, was measured on a machine that never booted.

**A device may address only its own SRAM** (11fc717). The address was a plain add
of the pack's base and the mapper's offset, unbounded, so a device that ran past
its allocation walked into the next one and that corruption was written back to
the `.sav`. Out-of-range now reads FF and writes nothing.

**An auto-load request that cannot be served yet is kept** (15f31ad). Three ways
the boot `.sav` load was silently dropped: the bank was walked and marked done, a
read-only image refused to be read, and a request arriving on the same edge as a
completion lost one bank. All three are mutation-tested.

## 2. Open, in the order worth doing

1. **The guard in `docs/sram_load_guard.md` is designed but not built.** The machine
   is released 2.9 us after the `.sav` is asked for, while the read is 32 sectors
   (ST) or 64 (GT). The plan's step 1 — measure what the firmware writes in that
   window — has run twice and both times reported **zero BRAM writes at all**, which
   the bench's own sanity counter flags as an invalid measurement rather than a
   clean result -- and it was measured on a machine that never booted, because the
   bench truncated the pack at 2 MB. `PACKSZ` is `1 << 23` now and an oversized pack
   is fatal rather than silent. A longer run does NOT help either: both counters sit inside
   `if (load_flight)` and that clears when the load ends, so the window is the load
   itself and the number is a function of the guessed `SDSLOW`. Count ungated and
   stamp the first write instead; the deciding number is T_first against the real
   HPS load duration, which has to come off the board. **No RTL until both exist.**

   **VOID, 2026-09-27: there is no measurement here yet.** This section briefly carried
   "the FS-A1ST boot reaches 13,117 distinct PCs" and "no CPU WRITE into the SRAM window
   before 2.4 s". Both are **retracted**. Those runs were built from worktrees cut at
   `origin/nextz80`, which does not contain `a72ed9e` -- `git branch -r --contains
   a72ed9e` is empty -- so they ran the failed-firmware-search bug: MSX1-typed machine,
   no CONFIG, and no `.sav` served at all ("image -1, 0 sectors served", RESULT SKIP).
   No SRAM statement follows from a machine that never received an SRAM image. The
   positive control from those runs is void for the same reason: the detector needs
   `sav_idx >= 0` and no image was ever served, so its 0 reads say nothing about the
   detector either.

   **The runs said so themselves.** Their upload lines read `MSX_typ=0 ... load_sram
   issued=0` followed by `WARNING: a .sav is mounted but the upload never asked for it`.
   That is the third time in two days that a log stated the problem in words and was not
   read; see 2d. The rerun's acceptance check is now the first thing looked at rather
   than the last: `MSX_typ=1`, `load_sram issued=1`, no WARNING.

   Reruns are in flight from a worktree at local `nextz80` (734b731) merged with
   `origin/nextz80` inside the worktree, so it carries `a72ed9e`, `4590b37`, `10837af`
   and the stubs fix.

   Still valid, because neither came from those runs: the storm was `midi_int_n` (the
   `intsrc` run was at local HEAD, whose upload line shows `MSX_typ=1` and `load_sram
   issued=1`), and the fullsys VRAM stub defect, which is a code fact.

   **Verifying the guard in fullsys is not available as a plan yet.** The guard works by
   adding "load in progress" to `dma_active`, which reaches the CPU through
   `nvbak_dma_active` -> `msx_pause` (`MSX1.sv:878`). In `tb_msx.sv` both `msx_pause` and
   `dma_active` are assigned once in the `initial` block, to 0, and never again -- and the
   `nvram_backup` instance leaves `.dma_active()` unconnected, so the engine's own busy
   signal goes nowhere. So the bench could not show the guard working even once it is
   written. Building `msx_pause` the way MSX1.sv does, at least its `nvbak_dma_active`
   term, is bench work to do alongside the guard step.

   Keeping `msx_pause` at 0 for the T_first runs themselves is deliberate: a CPU that is
   never held is the worst case for the hazard, so the measurement is conservative. Note
   `upload_hold` is one of the real terms, so on hardware the CPU is held for the whole
   OSD upload and in the bench it is not -- again permissive in the safe direction.

   What that does NOT settle is whether the guard is a fix or a precaution, because write
   counting does not cover the hazard. A firmware READ of the SRAM window before the load
   lands is harmful with no write anywhere: the machine acts on stale or zero bytes --
   wrong locale, wrong screen mode, an "SRAM not initialised" decision -- and some of
   those consequences never touch the SRAM again, so no write counter can see them. The
   proposed guard already covers reads, because it is `msx_pause` and a paused CPU cannot
   read either; so the hazard set is larger than the instrument, and the fix/precaution
   call waits on read instrumentation. That is running: reads counted per access off
   `bram_ce`/`ram_rnw` against the same comparator, ST and GT to 8 s.

   **The window that decides it is the load, not the run.** An access after the `.sav` is
   in is harmless, so the question is whether anything lands inside 31.8 ms (ST) or
   311.1 ms. Nothing does, across the first 311 ms. The 8 s runs are measuring the MARGIN
   -- T_first against a real HPS `T_load` that can be far longer than the sim's -- which
   is worth having but is a different question, and a bound of 2.4 s against a few
   hundred ms of load probably settles the decision already.

   **The limit on the claim, and it is in the DUT and not the instrument.** The
   detector's wiring holds by construction: the bench returns BRAM data to the CPU only
   through `assign ram_dout = sdram_ce ? sdram_dout : bram_ce ? bram_dout : 8'hFF`
   (`tb_msx.sv:481`) and the BRAM write enable is `bram_ce & ~ram_rnw` (`:195`), so any
   CPU access that actually gets SRAM data asserts the same three signals the detector
   samples. Retargeting the comparator at a BIOS or main-RAM address does NOT test this,
   because those are SDRAM in fullsys (`sdram_ce`); the only CPU traffic reaching BRAM is
   the SRAM itself. One real limitation of the edge counter: back-to-back accesses with
   `bram_ce` held high undercount. The first-access stamp is unaffected.

   What is unmeasured is the path the claim depends on, so the claim carries a proviso:
   **no CPU access to the SRAM window before N s, PROVIDED the 3-3 mapper routes CPU SRAM
   accesses to BRAM.** If that path is broken the firmware cannot reach its SRAM, both
   counters stay 0, and "0 accesses" is a mapper defect wearing a timing result's clothes.

   The proviso is narrower than it first looks, and worth splitting because only one piece
   is actually unmeasured:

   - mapper -> `sram_cs` / `mem_addr`: **measured** at module level by
     `sim/run_panasonic.sh` (`OP_SRAM` checks `sram_cs` with the expected `mem_addr`,
     `OP_NOSRAM` checks it stays low, `OP_SRAMWE` checks the write strobe).
   - `sram_cs` -> `bram_ce`: one combinational line, `msx_slots.sv:250`. With SDRAM
     present it requires `sram_cs`, which is right, but it also requires
     `mapper != MAPPER_UNUSED` and **`~mem_unmaped`**.
   - `ram_addr`: `base_sram = lookup_SRAM[ref_sram].addr` (`:194`), with `ref_sram = 3`
     for the internal slot.

   So the specific thing to check first is `mem_unmaped`, because the SRAM bound I added
   to it earlier in this session (`sram_over = sram_cs & (mapper_addr_raw >= sram_bytes)`)
   suppresses `bram_ce` for any access it judges out of range. If `size_sram` were wrong
   for a 3-3 pack, every legitimate SRAM access would be silently unmapped and the
   counters would read 0 for that reason alone. The arithmetic looks right -- pack kB
   into `lookup_SRAM[].size`, `sram_bytes = size << 10`, and the Panasonic mapper's
   `{sel - 9'h080, cpu_addr[12:0]}` stays inside 16 kB for the ST's two banks -- but it
   is my own change from the same day, it sits directly in the path, and it has not been
   exercised through the machine. Log whether `mem_unmaped` ever asserts while `sram_cs`
   is high before trusting a zero.

   Closing the proviso properly needs real CPU stimulus through the mapper: select an
   SRAM bank, read a byte, write a byte. The bench cannot inject Z80 code today, so this
   belongs with the "mapper answering CPU accesses is unmeasured" item in 2b. On hardware
   the equivalent is trivial: settings that survive a power cycle.

   **And a clean run proves nothing until the detector is shown to fire.** "0 reads
   through 8 s" and "the read detector was never armed" produce identical logs. A control
   run is in flight that forces a read into the window and requires the stamp and the
   early stop, with its pass condition written down before the result. A forced-bus
   control proves the logic but not that the detector is wired to real CPU traffic;
   retargeting the comparator at an address the firmware certainly reads is the control
   that proves the wiring.

2. **8 kB quantisation in the Panasonic mapper.** `sram_kb >> 3` drops a remainder:
   a pack declaring 20 kB gets a 16 kB window and the last 4 kB is unreachable, with
   no warning, while the `.sav` is still sized 20 kB. ST 16 and GT 32 are multiples
   so nothing in the tree hits it. Worth a line in the doc and a check in the pack
   tool.
3. **The real SRAM ceiling is 64 kB** (`dpram #(.addr_width(16)) systemRAM`), shared
   by all four allocations, while `lookup_SRAM.addr` is 18 bits and suggests 256 kB.
   Nothing reconciles the two.
4. **Three mappers still hard-code their SRAM window** (FM-PAC, Game Master 2,
   Halnote) while Panasonic and the ASCII pair read `size_sram`. Giving them the
   size removes a class of pack/device disagreement.
5. **GT main-RAM banks (>= 0x180) in the Panasonic mapper** remain unimplemented and
   report unmapped. Deferred by the user; needs a pack that reaches them first.
6. **`memory_upload` fails silently on a bad header** — back to IDLE with no message.
   That silence hid an empty machine for a long time.
7. **`nvram_backup` image_size** was eight times too large (fixed in 11fc717) only
   because it is compared against zero. Anything that starts using it as a length
   should re-check.
8. **The four `CART_FW_*` packs** still need `GM2.ROM` and the MegaFlashROM image;
   two of the four now build from public files.
9. **`_2slot` firmware packs** need a genuine two-slot MegaFlashROM image.

## 2b. Fixed: memory_upload lost the rest of the pack after a failed MoonSound search

Resolved 2026-09-26. `sim/run_fwsearch.sh` shows it red before and green after, and the
two corrections are in `memory_upload.sv` at the two firmware-search return sites.

A device record for MoonSound with no inline ROM (`conf[7] == 3`, count 0) makes
`memory_upload` save its place, jump to the firmware store at DDR3 0x2000000 and look
for a pack there. Three paths come back, and only the one that actually found and filled
a ROM returned correctly. The other two -- end-of-store and "Havarie" -- were wrong in
*two* ways, not the one the reading had found:

1. They restored the address but left `save_addr` set. `STATE_READ_CONF` gates the
   end-of-pack test, and with it the `load_sram` pulse, on `save_addr == 0`.
2. They restored `save_addr` exactly, one byte too high. The success path comes back
   through `STATE_FILL_RAM`, which spends one DDR3 prefetch; these paths re-enter
   `STATE_READ_CONF` directly and so are one short. The next record was read from
   `save_addr + 1`, the "MSX" magic missed, and `STATE_CHECK_CONFIG` dropped to
   `STATE_IDLE` -- silently, since a magic mismatch there is the normal end-of-pack
   exit. This is the same one-deep pipeline that makes the FW header skip `+7` and not
   `+8`.

Clearing the flag alone changes nothing; the bench was red both ways until the `-1` went
in too. Had the one-line fix been applied on the reading alone, it would have looked
like the defect was something else.

The effect was that the pack tail was never recognised: no CONFIG, no KBD_LAYOUT, and on
a GT the MIDI device record too, since it sits after MoonSound. `bios_config.MSX_typ` is
written only by the CONFIG handler and its zero value is MSX1, so `vdp18` was handed the
TMS9918 on a turbo R, and `load_sram` never pulsed, so no `.sav` was ever requested. Both
shipped FS-A1ST and FS-A1GT packs carry the trigger, and 35 machine XMLs declare
MoonSound without an inline ROM.

What that does to the boot is NOT established. It is tempting to say a turbo R cannot get
through the BIOS's video init with MSX1 video, and this document said so; see 2c, which
disproves it as the cause of the interrupt storm.

**Confirmed end to end in fullsys, 2026-09-26.** On the unmodified ST 3-3 pack at
HEAD with no FW pack staged, the peer session's run processes `LOAD KBD LAYOUT` and
`STORE CONFIG MSX:1` (`MSX_typ=1`), reports `msx_device=11111` -- which now includes
MOONSOUND at bit 3 -- and loads the `.sav`: image 3, 32 sectors, 16,384 bytes into
SRAM, 0 wrong, load over at 31.80 ms, RESULT PASS. So the fix holds in the whole
machine and not only in `sim/run_fwsearch.sh`. (A `load_sram issued=0` line in that
log is the bench's own sampling race, fixed after that binary was built.)

**Why hardware still worked.** The condition is only ever met when the firmware store
holds no valid pack. The user confirmed an FW pack was loaded during the 2026-09-24
board session that `tools/turbor_diskrom/README.md:83` records, which is why Illusion
City and SD Snatcher ran. The contradiction was never in the code reading.

**Severity: low, and do not repitch it.** All four `CART_FW_*` XMLs declare the same
four `<fw>` entries -- FM_PAC, FDC, MEGA_FLASH_ROM, MOONSOUND -- and `createFWpack` is
all-or-nothing, so any FW pack that exists contains the MoonSound record and the search
always finds it. The only configuration that reaches the bug is a machine with no FW pack
loaded at all, and that machine has no MSX-MUSIC either, so nobody runs it on purpose: an
FW pack is in practice standard equipment. What the fix buys is a better failure mode --
a machine without a pack now boots as the right machine minus MoonSound, instead of a
turbo R silently wired to the TMS9918 with no SRAM saves -- and a fullsys that traces a
booting machine without needing a doctored pack.

**This changes the fullsys baseline, but it does not explain the interrupt storm.**
fullsys loads no firmware pack, so every run with an unmodified ST or GT pack was in this
state and its CONFIG, KBD_LAYOUT and `.sav` request were all missing. I wrote here that
the storm the peer session measured was therefore this defect. That was wrong, and the
peer disproved it: see 2c.

## 2c. Settled: the interrupt storm was `midi_int_n`, undriven

Cause: `e6e7e1c` added `midi_int_n`/`midi_rx`/`midi_tx` to `msx_slots` and did not
connect them at the `msx_slots` instance in `rtl/msx.sv`, so the net `msx.sv:1196` reads
0 and holds `/INT` low through `:292` and `:335`. Fixed on origin as **`4590b37`**.
The measurement that found it: at 1,041 interrupt acknowledges the low line was
vdp 0, moonsound 0, **midi 1041**.

It reached hardware. `MSX1_20260924c_midi.rbf` (md5 23ad4758b3fa) was put on a board and
never reached the GT opening screen, so "Quartus ties the undriven net to GND and the
machine hangs at its first EI" is observed, not argued.

**Everything this document previously said about the storm was wrong, twice.** First it
was attributed to a72ed9e's firmware search; the peer disproved that with `ST33_noms`.
Then both of us spent an afternoon on the VDP -- IE1, FH, R#15, `ENAHSYNC`, the S#1 read
-- and none of it was the cause. The elimination that worked was reading the three
`int_n` nets directly rather than reasoning about what could hold INT.

**And fullsys VRAM was dead until 2026-09-26.** `vram_lo`/`vram_hi` left `enable` and
`cs` unconnected and the `stubs.sv` spram had no defaults, so VRAM was never written and
always read FFh. That applied to every fullsys run before the fix. Any VDP-state
reasoning from before it is suspect, including all of the above.

## 2d. Two lessons that cost a board boot and an afternoon

**A tool said both things out loud and nobody read the log.** `midi_int_n` was left
unconnected by e6e7e1c and Quartus said so in every map report since:
`Warning 10030: net "midi_int_n" has no driver or initial value, using a default
initial value '0'`. It is in the audit session's own `full_v2b` log. Earlier the same
day, warning 10999 in my own log said the PCM header/dyn arrays had failed MLAB
inference, and I built a whole hypothesis on the assumption they were MLAB without
looking. Two defects in one day, both named explicitly by the tool, both missed because
the log was treated as noise.

**And a third time, the next day.** A set of fullsys runs was reported as a booting
machine with an SRAM measurement, from logs whose own upload lines said `MSX_typ=0`,
`load_sram issued=0` and `WARNING: a .sav is mounted but the upload never asked for it`.
The acceptance check existed, in words, in the output being quoted from. The fix is
ordering: check the preconditions the run prints BEFORE reading the result it prints,
and write the acceptance line down before the run.

**A suppression flag is a disabled detector.** `tools/lint_top.sh` carried
`-Wno-PINMISSING`, added to quieten 23 intended cases, and that flag switched off the
one warning that names this class of defect. Verilator's `PINMISSING` prints the three
missing pins by name on a broken tree. `4590b37` fixes the flag and adds
`tools/check_pins.sh` with `tools/pinmissing_baseline.txt`, so only NEW missing pins
fail. My bench scripts carried the same two flags for the same reason; `398cf04` and
`bb6afb7` remove them, and enabling the detectors cost nothing -- 0 port warnings, every
result unchanged -- while finding one real accidental tie (`hold_load` in
`tb_fwsearch`). `sim/golden/run_pcm_golden_vl.sh` still carries both and deliberately
leaves debug outputs unconnected, so it needs the baseline treatment rather than a
straight removal.

**The sweep nobody had run.** With the detectors on, the whole fullsys elaboration
reports **25** `PINMISSING`. Classified: the three MIDI pins (the defect, fixed on
origin); `clk_sdram` on the `msx_slots` instance, which is **vestigial** -- `flash.sv`
declares it and never uses it, one occurrence in the file and that is the declaration,
which is why flash carts work; and 21 unconnected OUTPUTS (`debug_*`, `dbg_*`,
`comp_sync_n_o`, `col_o`, `OFFSET_Y`, fdc's `prepare`/`busy`/`buff_*`, T80s `OUT0`,
jt49's `sample`, IKASCC `i_SCCP_MODE`, the bench's `SDRAM_CLK`/`ch3_*`), which are the
benign direction. Reproduce with a `--lint-only` pass over
`sim/fullsys/gen/filelist.txt` and the flag list from `sim/fullsys/run.sh` minus
`-Wno-PINMISSING -Wno-UNDRIVEN`; it needs no writes to the tree.

I expected `UNDRIVEN` to be the detector that mattered, on the reasoning that an
unconnected output is only dangerous when the parent reads the net -- which is exactly
what happened to `midi_int_n`. **It produced 0 warnings.** `PINMISSING` is the one that
names it here, so `tools/check_pins.sh` picked the right warning and the refinement I
was about to propose was built on an untested hypothesis. Quartus names it separately as
warning 10030.

**The same class, seven times, in one bench.** Every fullsys defect found in two days was
a constant or an omission standing in for something the machine derives:

| | |
|---|---|
| `PACKSZ = 1 << 21` | packs over 2 MB silently truncated; every CPU-side result void |
| the DDR3 model | followed the address instead of holding `ram_q`; the pack never parsed |
| `stubs.sv` spram | no defaults on `enable`/`cs`, so VRAM was never written and read FFh |
| worktrees cut at `origin/nextz80` | no `a72ed9e`, so no CONFIG and no `.sav` served |
| `.cpu_speed(3'd0)` | `MSX1.sv:637` makes it `use_nz ? 3'd4 : ...`, so NextZ80 ran ~6x slow |
| `msx_pause`, `dma_active` | fixed 0, so the machine is never held and the guard cannot be shown |
| `nvram_backup .dma_active()` | unconnected, so the engine's busy signal goes nowhere |

Two of those are `PINMISSING` cases, and `-Wno-PINMISSING` is in `sim/fullsys/run.sh`.
The rule to write down is narrower than "benches lie": **a hard-wired input to the DUT,
or an unconnected port on it, must be checked against the wrapper the bench replaced.**
fullsys leaves `MSX1.sv` out by design, so every signal that file computes is a bench
stand-in until someone diffs it.

## 2e. Open, a class: latched copies of an SDRAM allocation

Every upload re-walks the config from `ram_addr = 0` (`memory_upload.sv:669`) and
allocates sequentially (`:482`), so any module holding its own copy of an allocation can
be pointing at the previous layout. Two instances:

- `flash16x_base/size/active` (`msx_slots.sv:812-820`), latched on a `cpu_mreq` with an
  ASCII16X or Yamanooto mapper and cleared only by `reset`. Stale indefinitely, which is
  the defect `sim/run_staleflash.sh` case B demonstrates. Fix (2) is with the audit
  session; the shape they have converged on is to stop copying and feed the engine the
  allocation `memory_upload` just made, which reaches `MSX1.sv` directly with no port
  threaded through `msx.sv`/`msx_slots`.
- `mfrsd_base_ram` (`mfrsd.sv:18`, `if (cs) mfrsd_base_ram[cart_num] <= base_ram`),
  consumed at `mfrsd.sv:179` and `:252` as `mem_addr = mfrsd_base_ram + flash_addr` and
  at `msx_slots.sv:373` as `flash.sv`'s `sdram_offset`. **Not** the same severity: it
  re-latches on the very `cs` that uses it, so the skew is at most one access rather than
  indefinite, and `flash.sv`'s `ce` is gated on the same CPU-driven request. Whether that
  one-access skew can land inside a multi-access flash command sequence depends on when
  `flash.sv` samples `sdram_offset`, which has not been checked.

  The tell that this is worth fixing anyway is on that same line: for ASCII16X and
  Yamanooto, `sdram_offset` already takes the LIVE `base_ram`, and only MFRSD takes the
  latch. So the live value is in scope and already preferred by two of the three
  mappers. Making MFRSD use it too would retire this instance without new plumbing.

current engine and the flop-array reference are compared every cycle while
`+stress` fires slot-register writes at the races the MLAB version could get
wrong: the dispatch-read edge, header-backfill collisions, and the first cycles
after a warm reset during playback.  PASS also needs four mutants to fail in every
run, a reset held 8 cycles to fail (the engine clears its registers while in
reset and needs >= 24 clk), and every counted event to be non-zero.  The
invocation and the expected event counts are in that directory's README.md.
Golden and lockstep TBs now hold reset like the hardware does (300 / 256 cycles,
not 7-8); a 24-cycle minimum is load-bearing, see the comment at the sweep.

### `sim/run_uphold.sh` -- upload_hold: the OPL4 hold is FIXED, S3 is still open

Two groups, two owners. **HOLD** (T1-T5, R) is fixed: `a4541d9` deleted
`& ~|flash16x_active` from `upload_hold`, and the bench reports `hold: 0` at HEAD --
measured here independently of the session that made the change, against
`hold: 2` (T2, T3) on the commit before it. The CPU pause is restored along with the
OPL4 hold, and that is **not yet confirmed on hardware**: it needs its own build, and
the `MSX1_20260926_v2b.rbf` already delivered does NOT contain it.

**S3** (T2c) is still red and is fix (2), owned by the audit session: a per-cart gate
on the restore decision, only when the upload replaces that cart's slot. Its bench is
`sim/run_staleflash.sh`, whose `tb_staleflash.sv` and runner now belong to that
session. `FIX=1` here is a no-op since `a4541d9` -- the generator says so on stderr
and extracts as-is, so the bench works on both sides of that commit.

What the defect was, kept because the reasoning is the reusable part. The DUT is
generated by
`sim/mk_uphold_dut.py`, which lifts the `flash16x_active` latch out of
`msx_slots.sv` and the reset chain out of `MSX1.sv` verbatim and fails loudly if
either changes shape -- so the bench cannot drift from the source.

`upload_hold = reset_rq & status[64] & ~|flash16x_active` was written in 042cc0d as
the "S3 guard", and that commit states its purpose: "refuse the no-reset path
whenever a flash cart is involved", because `flash16x_active`/`base`/`size` are
cleared only by `reset` and `flash_dirtysave` reads the base live, so across a
no-reset cart swap the next `.sav` DMA would point at the departed cart's SDRAM.

The guard does not do that. It sits in `upload_hold`, but the no-reset path is
decided by `reset_raw`, which takes `reset_rq` only when `~status[64]` and never
looks at `flash16x_active`. So with a flash cart touched and the toggle at Yes the
guard removes the OPL4 hold and leaves the machine un-reset -- worse than either
behaviour it was choosing between:

  - the OPL4 runs live for the whole transfer (T2, T3: held 0 of 400 clk21m), which
    is exactly the SDRAM ch1/ch4 pressure the comment above `reset_ms` says has
    bitten this core twice, and for a FW PACK upload it is the
    `pcm_rom_base`-moving-under-a-live-PCM-fetch case that comment names;
  - the stale base stays armed (T2c), so S3 itself is not prevented.

`flash16x_active` is set by ONE `cpu_mreq` with an ASCII16X or Yamanooto mapper and
survives every later upload, so the trigger is: touch a flash cart, then load
anything from the OSD with the toggle at Yes and no machine reset.

One candidate was considered and rejected: moving the term to
`reset_raw = ... | (reset_rq & (~status[64] | |flash16x_active))`, so a flash cart
forces the reset path. It realised 042cc0d's stated intent and cleared this bench,
but it makes an OSD load reset the machine whenever a flash cart has been touched,
which is what the toggle exists to avoid. Rejected 2026-09-26 by the audit session's
user, and removed from `mk_uphold_dut.py` rather than left to be tried again.

### `sim/run_staleflash.sh` -- the end-of-upload restore writes at a stale base (OPEN)

Red 2/7 as shipped, green with `FIX=1`. Runs against `flash_dirtysave`, which is the
engine `MSX1.sv:1464` instantiates -- NOT `flash_dump_test`. The first version of this
bench used `flash_dump_test` and drew a wrong conclusion from it (see below), so check
the instance before trusting any result here.

`flash_dirtysave` latches its LOAD trigger: `load_pending` is set by
`load_req = status[39] | load_sram` and serviced when
`load_ready = load_pending & flash16x_active & ~upload_active & image_size > 0`.
`load_sram` is memory_upload's end-of-upload pulse, so a restore is evaluated at the end
of every OSD load. The latch is deliberate and the comment at `flash_dirtysave.sv:139`
says why: unlatched, the pulse fell inside the stretched machine reset and "loading an
ASCII16X ROM never read its .sav".

That waiting is what makes a cold load correct, and the bench confirms it: case F
restores 64 kB at the new cart's own base, because the request waits until the first
ASCII16X access arms `flash16x_active` and refreshes `flash16x_base` on the same edge.

Case B is the hazard. With "Reset on ROM change" = No, swapping away from a flash cart
to a NON-flash one leaves the pair armed and stale -- nothing refreshes it and no reset
disarms it -- so `load_ready` is true at once and the restore writes the departed cart's
`.sav` at the departed cart's address: 65,536 bytes at `OLD_BASE` while the new cart sits
at `NEW_BASE`. If the slot reuses its staging area the victim is the ROM just loaded.
Cases S and Y confirm both workarounds: a machine reset between the two carts, or
leaving the toggle at its default Yes.

`FIX=1` models the candidate, and it gates the RESTORE REQUEST only:
`load_req & ~(flash16x_active & upload_replaced_this_cart's_slot)`. The slot is knowable
from memory_upload's `curr_conf`/ioctl index, so this needs one bit per cart and no
signal threaded into `msx_slots` -- which is what 042cc0d wanted to avoid. As shipped
the bench is red 2/9; with the gate it is 0, and `active` still reads 01 in case B,
which is the tell that the gate and not a reset is doing the work.

Two earlier versions of this were wrong, and the cases that catch them are now in the
bench:

  - Gating the engine's `flash16x_active` instead of the request. That input gates FOUR
    things -- `save_start` (123), `auto_start` (125), `load_ready` (128) and the DIRTY
    CAPTURE at 155. Gating it stops recording dirty blocks for a cart that is still
    inserted while an upload targets another slot, so writes in that window go missing
    from the next save: data loss, in the very case the guard exists to protect. Cases W
    (an upload elsewhere must still let the inserted cart restore) and D (a flash write
    in that window must still be saved) exist for this, with `prog_we` driven. The
    blunt version passes F/B/S/Y and fails W and D.
  - A plain freshness test on `flash16x_active` would kill the cold-load restore, since
    case F depends on the request WAITING for the arm.

Bench hygiene, learned here the hard way: `FIX=1` for this bench must not reach
`sim/mk_uphold_dut.py`, which reads the same name for run_uphold's candidate. It did at
first, so `FIX=1` silently rewrote `reset_raw` in the extracted RTL, forced a machine
reset during the upload, and every case went green for the wrong reason -- including a
green I had already reported. The runner now calls the generator with `env -u FIX`.

Related, and how the bench first misled itself: a latched request is not cleared by
`reset`, only by `log_clear` or by starting. So a pending restore survives a machine
reset and fires at the next flash access, with whatever base that access sets. That is
not benched as a case of its own yet.

Also measured here, independently of the PCM work: a machine reset holds `reset_ms`
for 65 clk21m = 260 clk_sdram, which is the margin the v2b register-file sweep needs
(>= 24 clk).

## 5. Traps worth not rediscovering

- **A bench that passes against a deliberately broken build proves nothing.** It
  happened twice here. The first `.sav` cases chained through the engine, which sat
  in `STATE_PROCESS` from the first load, so every later case asserted against an
  engine that never reached the decision under test. Isolate each case with a reset,
  and run the mutation.
- **`$display` with a ternary picking between two string literals prints nothing**
  in Verilator. Two benches lost their summary line to it.
- **A comment opening with the tool's own name is read as a pragma.**
- **openMSX settings are global Tcl variables.** A plain `set` inside a proc makes a
  local of the same name; it reads back as what you wrote while the setting keeps
  its default. Use `uplevel #0`.
- **`puts` in an openMSX script goes to openMSX's console, not stdout.**
- **Do not edit a long-running shell script while it runs.** bash re-reads it.
- **Verilator output is block-buffered to a file.** Silence is not a hang; check CPU
  time.
