# OPL4 (YMF278B) from-scratch 재제작 계획

작성 2026-10-24, **목표 개정 2026-10-27(사용자 확정: 고정 시각 + 두 슬롯 앞선 요청, sdram_tdm 중재 무변경, (b) BL2 word1을 ch4로 넘김 채택, 보장 범위는 처리량 기준)**: 메모리를 "가변 지연 핸드셰이크"에서 "정해진 시각 소비 + 두 슬롯 앞선 요청"으로 바꿈(사용자 결정, msx1-handoff 조율). 개정 전 목표 6이 슬롯 대기 → 프레임 예산 → 최악 L → sdram 우선순위·플래시·OSD로 번진 출발점이었다. 대상 저장소: MSX1_MiSTer, 작업 기준 브랜치 V9968_Geo3D (worktree `~/data/MiSTer_build/sdram128`).
기존 구현: `rtl/peripheral/SOUND/ymf278b_fpga/` (OPL3 FM = gtaylormb `opl3`, PCM = `rtl/pcm/ymf278_pcm_engine2.sv`, "v3 sequential slot machine").

128.86 MHz에서 44.1 kHz 한 프레임은 **2,922 클럭**이다. PCM 24슬롯이면 슬롯당 약 121클럭, FM 36 오퍼레이터까지 넣어도 시간이 남는다.
현재 엔진은 85.9 MHz의 72클럭 슬롯 창(1,948클럭 프레임)을 전제로 설계된 뒤 128 MHz로 끌어올려졌다. 시간 예산이 1.5배인데 면적을 줄이는 쪽으로 쓰지 못했다.

## 1. 목표 (게이트로 판정)

1. **비트 정확**: PCM은 openMSX `YMF278.cc` 포트(`sim/golden/ref278.cpp`)와 샘플 단위 일치, FM은 Nuked-OPL3와 일치(현행 수준 이상).
2. **드롭인**: `ymf278b_top`의 포트, I/O 의미(7Eh/7Fh, C4h-C7h, 상태/BUSY/타이머/ID, reg 0x02-0x06 메모리 접근, 헤더 재배치, DAMP, pseudo-reverb, LFO, F8h/F9h 믹스)를 그대로 유지. 새 PCM 엔진은 `ymf278_pcm_engine2`와 **같은 모듈 포트**를 갖는다(기존 벤치가 그대로 돈다).
3. **면적**: PCM ≤ 1,200 ALM, MoonSound 전체 ≤ 2,500 ALM (FM을 재제작할 경우). M10K는 MoonSound 합계 ≤ 20, 그중 PCM ≤ 6(2026-10-26 사용자 결정으로 "현재 15개 이하"를 폐기: M10K는 553개 중 323개 사용 58 %, 빠듯한 쪽은 ALM 81 %. `resource` 게이트가 판정), DSP ≤ 4.
4. **타이밍**: 128.86 MHz 단일 클럭 내부 경로는 SDC 예외 없이 통과. CDC는 문서화된 동기화기만.
5. **CPU에 보이는 시간**: 메모리 쓰기 BUSY는 **쓰기가 SDRAM에 실제로 반영된 시점**에 내린다(현행은 엔진이 쓰기를 *발행*할 때 내림: `ymf278_pcm_engine2.sv:1703,1722`, 그래서 `MEM_WRITE_DELAY`가 그 틈을 덮고 있다). 그 위에서 CPU WAIT은 openMSX 수준(약 0.83 µs = 107 clk). BUSY 상한은 구조적으로 보장(현행 v3의 장점 유지).
6. **메모리 (개정)**: `sdram_tdm`의 중재·명령 타이밍은 바꾸지 않고, 읽기의 BL2 word1을 넘기는 포트(`ch4_dout16b`)만 더한다(채널당 미결 요청 1개, 요청 하나 = 정렬 쌍 하나).
   엔진은 슬롯마다 **정해진 시각에** 웨이브 데이터를 소비하고, 그 데이터의 ch4 요청은 **두 슬롯(약 242 clk) 앞서** 낸다.
   ch4 지연이 앞섬 − 처리 시간 이하이면 출력은 지연과 무관하다. 넘으면 그 보이스만 직전 샘플을 유지하고 **늦음 카운터**가 오른다(위치·EG는 정상 진행, CE-stall 없음).
   보장 범위(아래 7) 시나리오에서 늦음 카운터 0이어야 PASS.
   - 낡은 선행 데이터: 요청 뒤 소비 전에 CPU가 그 슬롯의 주소에 영향 주는 레지스터(키온, 웨이브 번호, FNUM/옥타브, 위치 리셋)나 샘플 RAM을 쓰면 다시 읽는다. 다시 읽기는 슬롯 스케줄 여유(목표 8)로 흡수.
   - 헤더 로드 연쇄(웨이브 번호 → 헤더 → 샘플): "헤더 로드 뒤 몇 샘플부터 새 음"을 SPEC에 golden_pcm.py 의미대로 적고, 그 안에서 끝나게 스케줄.
7. **최악 기준 (신설)**: 보장 범위 = BUSY/LD를 지키는 소프트웨어가 할 수 있는 모든 것(24음, 높은 옥타브, 16비트 홀수 시작 주소, 매 프레임 루프 경계, 프레임당 메모리 쓰기 27, 헤더는 LD 간격, R800 최대율, 리프레시, VDP 부하). 범위 밖(멈춤 없음 + 손상 범위를 문서화) = LD 무시 헤더 폭주, 재생 중 플래시 섹터 지우기, autosave/dump, 업로드. 범위 밖 항목의 코어 쪽 대책(플래시 지우기 속도, OSD 일시정지 얼림, 업로드 리셋 확인)은 이 작업이 아닌 별도 할 일.
8. **슬롯 스케줄 여유 (신설)**: 슬롯 121 clk 중 정상 경로는 60~80 clk만 쓰고 나머지는 다시 읽기와 정확성 수정 자리로 비워 둔다.

비목표: 85.9 MHz 빌드 지원(128.86 MHz 전용), 15 kHz/ESE 빌드 전용 최적화.

## 2. 아키텍처 방향 (P1에서 확정)

- **시간 다중화 단일 데이터패스**: 슬롯 상태는 MLAB/M10K, 연산 자원은 덧셈기 1~2개 + 18x18 DSP 1개 + 시프터 1개. 슬롯당 고정 마이크로시퀀스(약 100클럭 예산, 여유 20%).
- **레지스터 파일**: 슬롯 레지스터는 현행처럼 per-byte MLAB(검증된 방식, reset 중 클리어, `reset_ms >= 24 clk` 전제). Quartus가 실제로 RAM으로 추론했는지는 **map 보고서 RAM summary**로만 판정.
- **메모리 접근 (개정)**: 목표 6. 슬롯 버리기(abandon), 프레임 예산의 L 항, 워드 캐시는 설계에서 빠진다(워드 캐시는 아래 처리량 계산이 허락할 때만).
- **열린 문제 — 처리량 (산술, 측정 아님)**: 앞섬은 지연의 흔들림만 흡수하고 처리량은 늘리지 않는다. 미결 1개라 ch4 처리량은 프레임당 2,922 / (L+2) 요청이다.
  요청 수 (`ref278`/openMSX `getSample` 주소식, 요청 하나 = 워드 / (b) 적용 시 정렬된 4바이트 쌍):
  - 보간 쌍 (pos, pos+1): 8비트 2바이트 → 워드 ≤2 / 쌍 ≤2. 12비트 pos 짝수 3바이트, pos 홀수 4바이트(3k+1..3k+4) → 워드 ≤3 / 쌍 ≤2. 16비트 4바이트 → 짝수 시작 워드 2, 홀수 시작 3 / 쌍 ≤2.
  - 루프 경계: 두 위치에서 **각각 샘플 하나만** 필요 → 워드 ≤2+2 / 쌍 ≤2+2.
  - 실제 내용: yrw801 ROM 헤더 384개 중 비어 있지 않은 330개가 12비트 328, 8비트 1, 형식 3 1; 시작 주소 mod 4 = 0/1/2/3이 90/76/93/70 (`~/.openMSX/share/extensions/yrw801.rom` 집계). **ROM 음색은 12비트, 정렬 임의**라 워드 3요청이 실제로 나온다.
  - CPU 메모리 연산 프레임당 최대 27(BUSY 기준 쓰기), 헤더(LD 준수) 프레임당 최대 1개 = 워드 6 / 쌍 3.

  | 경우 (24음 모두) | 워드 요청 | 맞는 L (2,922/n − 2) | (b) 쌍 요청 | 맞는 L |
  |---|---|---|---|---|
  | 12비트 ROM 음색, 높은 옥타브, 루프 경계 가끔 + 쓰기 27 + 헤더 1 | 72+27+6 = 105 | ≤ 25 | 48+27+3 = 78 | ≤ 35 |
  | 16비트 짝수 시작, 같은 부하 | 48+33 = 81 | ≤ 34 | 48+30 = 78 | ≤ 35 |
  | 매 프레임 루프 경계(루프 길이 < 증분) | 96+33 = 129 | ≤ 20 | 96+30 = 126 | ≤ 21 |

  측정 L(sim)은 중앙 20 / p99 29 / 최대 40. (b) 없이는 ROM 음색 24음 고음에서 p99도 못 맞춘다. (b)가 있으면 p99는 맞고, 최대 40은 두 슬롯 앞섬(버퍼)이 흡수하는지 sim으로 볼 일. 매 프레임 루프 경계는 어느 쪽이든 미결 1개로는 못 맞춘다 → 범위 밖 후보.
  **결정 (2026-10-27)**: (b) 채택. 보장 범위 = (b) 전제, L = p99에서 ROM 음색 24음 고음 + 재생 중 업로드(쓰기 27/프레임) + LD 준수 헤더 → 늦음 카운터 0. 범위 밖 = 매 프레임 루프 경계, L 급등(플래시 지우기 등), LD 무시 헤더 폭주 → 카운터 계수, 손상은 그 보이스 한 샘플.   - 읽기: 보장 범위의 L = fullsys p99 31(최대 40). 벤치의 103~191은 중재의 **합성 최악**(12프레임 연속 V를 반복하는 패턴은 V9968이 만들지 않음, 위 fullsys 측정)으로 범위 밖 설명에만 쓴다: 앞섬 242 clk 안에서 그런 요청 하나는 흡수되고, 둘 이상 겹치면 늦음 카운터가 센다.
  - 회귀: (b)를 넣은 sdram_tdm으로 `sim/v9968_vram/run.sh`(MS=20; MS=0이면 정답 phase도 FAIL하는 것이 정상) → RELEASE_PH 5만 PASS, 지연 8: 19,478, bad 0, `RESULT PASS: exactly one phase`.
  대책: (a) 슬롯별 직전 워드/쌍 보관(느린 보이스의 요청을 줄임, 최악은 못 줄임), (b) sdram_tdm이 이미 버스로 받는 BL2 word1을 ch4로 넘김(중재·DQM·명령 타이밍 무변경, 16비트 레지스터 + 포트 추가, `TDM_MUT_CAP` 자리; 공유 모듈 회귀 필요), (c) 매 프레임 루프 경계를 보장 범위에서 뺌. 낡은 선행 데이터 감지는 **주소 비교**여야 한다(전역 "쓰기 있었음" 플래그면 쓰기 27 × 선행 쌍 4 = 108 다시 읽기로 넘침).
- **FM**: P6에서 결정. 선택지 (a) gtaylormb 유지, (b) 같은 시퀀서 위에 36 오퍼레이터 시분할(Nuked 대조). (b)는 면적 이득이 크지만 위험도 크다.

## 3. 단계

| 단계 | 내용 | 끝나는 조건 (게이트) |
|---|---|---|
| P0 사양 고정 | 현행 v3/v2의 "하드웨어 검증 의미론" 목록, openMSX와의 의도적 차이(eg_cnt 오프바이원, EG_OFF LFO, vib ÷12 절단)를 `SPEC.md`로 정리. 실제 소프트웨어 레지스터 트레이스(openMSX에서 MoonBlaster/vgmplay/OPL4 데모) 수집 | 사양 항목마다 테스트 시나리오 이름이 붙음 |
| P1 하네스 먼저 | `opl4-harness` 스킬의 게이트 전부가 **현행 엔진으로 PASS, 뮤턴트로 FAIL** | `harness.sh all` PASS + `harness.sh mutants` 전부 FAIL |
| P2 골격 | CPU 인터페이스, 레지스터 파일, 메모리 읽기/쓰기, 상태/BUSY | G-cpu, G-busy, G-reset |
| P3 데이터패스 | 스텝/보간/EG/LFO/팬/믹스 | G-golden(ref278 + golden_pcm.py) 전 시나리오 비트 일치 |
| P4 통합 | `ymf278b_top`에 연결, 기존 엔진과 CPU 가시 출력 lockstep, fullsys (OPL4 감지, vgmplay freeze, PCM 업로드) | G-lockstep, G-fullsys |
| P5 면적/타이밍 | Quartus map-only → fit, ALM/RAM 게이트, STA | G-resource, G-timing |
| P6 FM 결정 | (a)/(b) 중 선택, (b)면 Nuked 골든 | G-fm |
| P7 보드 | 결정적인 한 번: 체크리스트(아래) 녹음 비교 | 사용자 확인 |

각 단계는 별도 커밋. 엔진 교체는 `ifdef`가 아니라 qip 파일 교체로 하고, 기존 엔진은 lockstep 오라클로 저장소에 남긴다.

## 5. 알려진 함정 (이 프로젝트에서 실제로 밟은 것)

- 컴파일 실패가 이전 바이너리를 남겨 "ALL MATCH"가 나온 적이 있다 → 빌드 디렉터리 통째 삭제 후 빌드, 바이너리 없으면 FAIL.
- `ramstyle`을 붙인 배열이 generate 안에서 **경고 없이** 플립플롭이 됐다 → RAM summary로 판정.
- 고정 인덱스 디버그 읽기 포트가 RAM 추론을 깼다(경고 10999) → 디버그 포트는 별도 스냅샷 레지스터로.
- 레지스터 파일 클리어는 reset 길이에 의존(≥ 24 clk) → `run_stress.sh`의 reset_len=8 must-fail 케이스 유지.
- 골든 시나리오는 슬롯을 읽는 순간 근처의 레지스터 쓰기를 거의 만들지 않는다 → stress 벤치 필수.
- 시뮬레이션 stdout이 줄을 잃을 수 있다(`cmp_time.sh` 참고) → 결과는 파일로 남기고 파일에서 판정.
- Quartus 작업은 한 번에 하나. 보드 테스트는 비싸다: 시뮬레이션 양/음성 대조로 먼저 결론.

## 6. 보드 체크리스트 (P7)

1. MoonSound 감지 (BIOS/툴의 OPL4 ID, reg 0x02 ID 비트)
