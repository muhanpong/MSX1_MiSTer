## 1. 골든이 정하는 시간 제약 — 왜 두 단계인가

`tb_golden_pcm.sv`는 프레임 N의 쓰기를 프레임 N−1 안의 정해진 클럭(`apply_cycle`, 1,948 clk 프레임 기준 값을 2,922로 환산)에 넣고,
모델(`golden_pcm_omsx.py`)은 그 쓰기를 **프레임 N 전체에 한꺼번에** 적용한다(헤더 로드도 쓰는 순간 동기).
시나리오의 `apply_cycle`은 1000-1870 → **1,500-2,805 clk** (측정: `sc_*.txt` 4열 집계. 1780 = 2,673은 `sc_pitchbend`, `sc_dirdep_bad`, 1870 = 2,805는 `sc_memwrite`의 reg 6 쓰기).
`do_write` 한 번이 3 clk이고 한 프레임 쓰기는 이어서 나가므로, 마지막 쓰기가 끝나는 시점은 **2,808**(`sc_memwrite` 프레임 40, 쓰기 7개), 가장 이른 쓰기는 1,500이다(모든 `sc_*.txt`를 이 규칙으로 집계. 프레임 40의 쓰기 7개는 1700/1720/1740/1750/1790/1830/1870이라 마지막만 2,805에 들어가고, 일곱 개가 2,805부터 이어져 2,826까지 가지는 않는다).

따라서 엔진은 다음 둘을 지켜야 비트 일치한다.

1. 프레임 N의 모든 슬롯이 레지스터를 읽는 순간은 **프레임 N−1의 2,805 뒤, 프레임 N의 1,500 앞**에 있어야 한다(그 사이에 다음 프레임 쓰기가 끼면 안 된다).
2. 메모리를 쓰는 시나리오(`sc_memwrite` 3보이스, `sc_memhit` 2보이스)에서 프레임 N의 샘플 읽기는 같은 창 안에 끝나야 한다.

"슬롯 s를 프레임 안 s × 121.75 clk에 처리"하는 단순한 고정 시각표는 1을 어긴다(슬롯 12 이후는 1,500 뒤에 레지스터를 읽는다).
engine2는 24슬롯을 프레임 앞쪽에 몰아 처리하고 뒤를 서비스 창으로 비워 이 제약을 지켰지만, 그 대가가 가변 지연 핸드셰이크였다(버린 설계).

그래서 슬롯 처리를 둘로 나눈다.

- **A 단계 (제어)**: 레지스터와 슬롯 상태를 읽어 피치·위치·EG·LFO·TL·이득을 계산하고, 필요한 메모리 쌍 주소를 정해 요청 대기열에 넣는다.
  24슬롯을 **프레임 경계 근처에 몰아서** 돈다 → 제약 1. 메모리를 기다리지 않는다.
- **B 단계 (데이터)**: 슬롯마다 **정해진 시각 C_s**에 도착한 쌍에서 샘플 두 개를 꺼내 보간·이득·팬·누산한다. 메모리 요청은 A가 계산을 마친 즉시 나가므로 C_s보다 앞서 있다.
  데이터가 C_s까지 안 왔으면 늦음 처리(5절).

A가 몰려 있어도 메모리 요청은 B의 시각표(프레임 전체)에 맞춰 퍼져 소비되므로 ch4 처리량 계산(PLAN §2 표)은 그대로다.

## 2. 구조

```
 CPU ─▶ RAM-R (240×8, CPU 가시 레지스터) ──▶ A 단계 ──▶ RAM-S (슬롯 상태 + 헤더)
                    ▲  백필                    │  ALU 24b, 시프터, 표, DSP#2(attack·AM)
 헤더 페치 ─────────┘                          ├──▶ 요청 FIFO (MLAB 16 × 28b) ─▶ 메모리 시퀀서 ─▶ msx.sv 브리지 ─▶ sdram_tdm ch4
                                               └──▶ RAM-PD: 계획 워드 ◀── 응답 쌍(32b) ◀──┘
                                                         │
                                                  B 단계 (C_s마다): 디코드, 보간, ×env, ×TL, 팬 L/R, 누산  DSP#1
                                                         │
                                                  프레임 끝: F9h 믹스, 포화, pcm_valid
```

| 저장소 | 모양 | 내용 | 비고 |
|---|---|---|---|
| RAM-R | 240 × 8 SDP, M10K 1 | CPU 레지스터 08h-F7h (레지스터 하나 = 워드 하나) | P2 골격 그대로(부록 B) |
| RAM-S | 96 × 40 SDP, M10K 1 | 슬롯당 4워드: pos, stepPtr, env/state, TL_cur, lfo_cnt / 헤더 start·loop·end·bits | |
| RAM-PD | 144 × 40 SDP, M10K 1 | 슬롯당 계획 2워드(B가 쓸 것 전부) + 데이터 4워드(쌍 0-3, 32비트) | B 단계만 읽음 |
| 이전 샘플 | 24 × 16 MLAB | 늦음 처리용 보간 결과 | B 단계만 씀 |
| 요청 FIFO | 16 × 28 MLAB | {쌍 주소 20, 슬롯 5, k 2, 회차 1} | A가 넣고 시퀀서가 꺼냄 |
| 슬롯 플래그 | FF | key_retrig, pos_rst, hf_pending, bf_dirty[5](P2 그대로), 쌍 valid 24×4, 회차 24, 소비됨 24 | |

연산 자원은 단계별로 따로 둔다(공유 중재를 없애 시각표를 결정적으로).
A: 24비트 ALU 1, 시프터 1, 표(LUT ROM), DSP 1(attack `(~env×inc)>>4`, AM 깊이). B: DSP 1(보간, ×env, ×TL, ×gl, ×gr를 연달아), 24비트 덧셈기 1.
"한 상태 = 연산 1개" 규칙(128.86 MHz, SDC 예외 없음)은 그대로.

## 3. 시각표 (프레임 2,922 clk, `frame_cycle` 기준)

| 기호 | 값 | 뜻 |
|---|---|---|
| K | 2,850 (앞 프레임 안) | 프레임 N의 A 단계 시작 = 레지스터 확정 시점. 골든 마지막 쓰기 2,805 + `do_write` 3 clk × 연속 쓰기 여유 |
| A_s | K + Σ(앞 슬롯 처리 시간), 슬롯당 40~50 clk(추정), 건너뛰는 슬롯(S-SKIP)은 약 5 | |
| A 끝 | 보통 K + 1,200 = 프레임 N의 1,128 | 골든 다음 쓰기(1,500)보다 앞 |
| C_s | 190 + 116 × s (C_0 = 190, C_23 = 2,858) | B 단계 소비 시각. B 처리 약 25 clk |
| 출력 | 2,921에 `pcm_valid` | engine2와 같은 위치(골든 TB 프레임 계수) |

확인할 부등식(산술; P3에서 TB 단언으로 넣는다):

1. **골든 창** (골든 TB 부하에서): K > 2,808, A 끝 < 1,500. 보통 1,128. 헤더 폭주(`sc_songchange24`, 아래 4)도 지연 20에서 약 1,150.
   실기 보장 범위(쌍당 약 35 clk, CPU 쓰기 27)에서는 시퀀서 점유가 78 × 35 = 2,730 / 2,922 = 93 %라 FIFO가 차서 A가 멈추고, A 끝은 프레임 N의 약 2,000까지 늘어난다(msx1-handoff 산술). 실기에는 골든 창이 없으므로 의미는 F-REG대로이고, 마감은 지킨다: 발행 순 = 마감 순, 마지막 쌍 도착 약 2,130 < C_23 = 2,858.
2. **앞섬**: 슬롯 0이 가장 짧다. A_0 요청 ≈ K + 25 = −47 → C_0까지 **237 clk**. 슬롯 s는 237 + s × (116 − A 슬롯 시간) ≥ 237.
   측정한 모델(앞섬 243, 최소 여유 156)과 같은 수준이고, 슬롯 1부터는 더 길다. PLAN 목표 6의 "두 슬롯 앞서"를 "계산 즉시 요청, 최소 237 clk"로 구체화한 것이다.
3. **덮어쓰기 금지**: A가 슬롯 s의 계획/데이터 워드를 쓰기 전에 B가 앞 프레임의 슬롯 s를 소비했어야 한다. 시간상 프레임 N 시작을 0으로 두면 K = −72, A_s ≥ −72 + 5s, C_s(앞 프레임) = 190 + 116s − 2,922 → 차이 ≥ 2,660 − 111s > 0 (s = 23에서 107). 그래도 시간에 기대지 않고 **소비됨 플래그로 인터록**한다(A는 소비됨(s)일 때만 s를 시작).
4. **헤더 폭주 (load 게이트, `sc_songchange24` 지연 6·10·20)**: 한 프레임에 쓰기 96개(웨이브 번호 24개)가 1,500부터 들어온다. 지연 20이면 헤더 하나 = 쌍 3 × 22 = 66 clk.
   K까지 1,350 clk에 헤더 20개가 끝난다. K 뒤에는 마감 순(4절): 슬롯 0-19 샘플 40쌍(약 880 clk, 약 830까지) → 슬롯 20-23 헤더(마감 C_s − 120 ≥ 2,200, 약 1,100까지) → 슬롯 20-23 샘플(약 1,280까지).
   C_20 = 2,510보다 한참 앞이고 A는 약 1,150에 끝난다(< 1,500). 산술상 들어간다(**TB 조건**: 브리지 없음, 쌍당 22 clk. 실기 쌍당 약 35면 K 전에 끝나는 헤더는 12개이고, 나머지는 F-REG대로 다음 프레임). 헤더를 샘플보다 무조건 앞세우면 슬롯 0-1 샘플이 헤더 24개(K 뒤 약 160까지) 뒤로 밀려 C_0 = 190을 넘는다 — 그래서 마감 순이다. engine2는 이 게이트를 XFAIL로 두고 있다(H4).
5. **메모리 원자성 (골든)**: 메모리 쓰기 시나리오는 보이스 2-3개 → 프레임 N 읽기 6-12쌍이 K 뒤 약 300 clk 안에 끝, 1,500 전. 보이스가 많고 지연이 긴 실제 기계에서는 프레임 N 읽기가 1,500 뒤까지 갈 수 있다 → 그때 CPU 메모리 쓰기는 "다음 프레임 또는 지금 프레임의 남은 읽기"부터 보인다(5절, SPEC F-MEM). 골든 범위 밖이고 한 프레임 안의 일이다.

## 4. 메모리 시퀀서

- 요청 하나 = 정렬 4바이트 쌍(`mem_addr[1:0] = 0`). 응답은 word0 = 바이트 0-1(`mem_rd_data16`), word1 = 바이트 2-3(`mem_rd_data16b`, 새 포트).
- 슬롯 하나의 쌍: 샘플 A(pos)와 B(pos+1 또는 루프 경계 뒤)의 바이트 범위가 걸치는 정렬 쌍, 중복 제거 후 1-4개. 보통 1-2, 루프 경계에서 최대 4(PLAN §2 계산).
- 우선순위(미결 1개, 한 요청이 끝나야 다음): **CPU 메모리 연산 > 마감 이른 쪽(헤더 쌍 vs 샘플 FIFO 머리)**. CPU 연산이 먼저인 이유: BUSY 상한(S-BOUND)과 WAIT ≈ 107 clk 목표. 프레임당 최대 27이 처리량 표에 이미 들어 있다.
  마감: 샘플 쌍 = 그 슬롯의 C_s, 헤더 쌍 = 그 슬롯의 다음 C_s − 120(A 마감). 13비트 시각 두 개 비교(빼기 2, 비교 1). 측정한 모델(CH4GEN)도 마감 순이었다.
- 응답 태그 {슬롯, k, 회차}: 회차가 슬롯의 현재 회차와 다르면 버린다(늦게 온 앞 프레임 응답). C_s가 지난 슬롯의 FIFO 항목은 내지 않고 버린다(소비됨 플래그).
- 브리지 배선: `sdram_tdm.ch4_dout16b` → `MSX1.sv` `pcm_sdram_dout16b` → `msx.sv` 입력 → `ms_mem_rd_data16b` → `ymf278b_top` → 엔진 `mem_rd_data16b`. 브리지 state 3(`ms_mem_rd_valid`)은 `ch4_ready` 상승 다음 clk이므로 word1이 그때 유효하다(sdram_tdm 주석과 일치). 브리지에 레지스터 추가 없음.
- 처리량(측정 반영): 보장 범위 프레임당 78요청(쌍 48 + CPU 27 + 헤더 3), L p99 31 + 브리지 → 계획 패턴에서 늦음 0, 최소 여유 156(0절). 범위 밖(매 프레임 루프 경계 126요청, L 급등, LD 무시 헤더 폭주)은 늦음 카운터가 센다.

## 5. 늦음, 헤더 연쇄, 낡은 데이터

- **늦음**: C_s에 슬롯 s의 필요한 쌍이 다 valid가 아니면, B는 그 슬롯의 이전 보간 샘플(이전 샘플 MLAB)에 **이번 프레임의 이득·팬**을 곱해 누산하고(그 프레임이 키온·재트리거·위치 리셋 직후면 이전 샘플은 다른 음이므로 **0**을 쓴다: A가 계획 워드에 에지 플래그를 실어 B가 이전 샘플을 0으로 지운다) `late_cnt`(16비트 포화)를 올린다. 위치·EG·LFO는 A가 이미 정상 진행했다. CE-stall 없음, 다른 슬롯 영향 없음. 손상 = 그 보이스 한 샘플.
- **헤더 연쇄**: 필드 0 쓰기 → hf_pending → 시퀀서가 헤더 쌍 3개(wave × 12는 4의 배수라 정확히 3쌍) → RAM-S 헤더 + RAM-R 필드 5-9 백필(bf_dirty 마스크, P2 그대로).
  A는 hf_pending인 슬롯을 건너뛰고 패스 끝에서 다시 본다. **A 마감** = C_s − 120(쌍 2개 + 여유)까지 헤더가 안 오면 그 프레임은 S-STALL: 출력 0, 위치·EG 정지(engine2와 같은 의미), `late_cnt` +1.
  보장 범위(LD 준수, 프레임당 헤더 1개)에서는 헤더가 다음 A 전에 끝난다: 3쌍 × (31+4) ≈ 105 clk.
- **낡은 선행 데이터 — 주소 비교가 필요 없어진 이유**: A는 요청을 계산 즉시 FIFO에 넣고, 시퀀서는 한 번에 하나씩 순서대로 처리하며 CPU 연산을 앞에 끼운다. 따라서 CPU 메모리 쓰기 뒤에 나간 읽기는 새 값을 본다. 쓰기 전에 이미 읽은 쌍(같은 프레임에서 아직 소비 전)은 옛 값을 쓰지만, 그것은 "프레임 N−1에 쓴 것은 프레임 N부터"라는 골든 의미와 같은 쪽이다(3절 5). PLAN §2의 "주소 비교로 다시 읽기"는 두 슬롯 앞선 요청이 프레임 경계를 넘어 레지스터를 미리 읽는 설계를 전제로 한 것이었다. 레지스터를 A가 한 시점(K 뒤)에 몰아 읽으므로 키온·웨이브 번호·FNUM/옥타브·위치 리셋에 대한 "낡은 선행" 문제도 없다: 그 쓰기는 다음 A부터 반영된다(SPEC F-REG).
- **S-MEMHIT**: 워드 캐시가 없으므로 매 프레임 새로 읽는다. (a) 직전 쌍 보관은 P5 fit 뒤 선택(PLAN 결정). 넣으면 그때 CPU 쓰기 주소 비교가 다시 필요하다.

### L 재측정 (F4)

- 원인: P2의 lprobe는 idle 루틴이 turbor.sv의 0180h-018Bh 덮개(CHGCPU `OUT (E5h),A; RET`) 위에 있어 idle이 한 번 돌고 CPU 모드까지 바꿨다. vprobe·mprobe_r는 이미 이 영역을 건너뛰고 있었다. lprobe를 0190h 뒤로 옮겼다.

- 대조: 옛 lprobe를 새 카운터로 돌리면 **INVALID**(phase 2 idle 1회 4.3프레임, phase 3 idle 2회 0.4프레임, phase 6·7 idle 1회).
- 새 lprobe(engine2, `/data/_claude/tmp/opl4-scratch/r6/lat3/lat.log`): phase 조건은 성립한다(key-on 24/0, idle 반복, 18-408프레임). 그러나 **LPROBE INVALID**: phase 2·4·5·6·7에서 앞 요청의 valid 전에 읽기 요청이 다시 오르는 일이 1-6회, valid를 못 받은 요청이 0-6개였다(phase 4: 상승 16444, valid 16438). 원인은 보지 않았다(engine2가 브리지 IDLE 복귀와 valid 사이에 요청을 내는지, 브리지가 그 요청을 버리는지).
- 참고값(무효 판정이므로 설계 입력 아님): 읽기 최소 17, 중앙 20, p99 29-33, 최대 40(phase 4·6). 쓰기 12/13-15/20/29.

### 요청 누락의 원인 (2026-10-27): msx.sv의 ch4 canary

- `msx.sv`의 ch4 읽기 무결성 canary(보드 디버그용 계측기)는 16,384 clk마다 "브리지 IDLE이고 엔진 요청이 없는" 사이클 c에 브리지를 잡는다(`can_owns`는 c+1부터 1). 엔진은 같은 사이클 c에 `mem_busy=0`을 보고 1 clk 펄스 요청을 내고, 그 펄스는 c+1에 나온다. 그때 브리지 mux(`br_rd_req = can_owns ? can_rd_req : ms_mem_rd_req`)가 엔진 요청을 가리고, 엔진은 valid를 영영 받지 못한다. engine2의 슬롯 FSM은 그 프레임 끝의 abandon(`E:737`)까지 멈추므로, 그 프레임의 남은 슬롯은 처리되지 않는다.
- 증거: phase마다 "canary가 브리지를 잡은 사이클에 오른 엔진 요청" 수 = 덮어쓴 타임스탬프 수 = 누락 수(phase 2·4·5·6·7에서 1·5·1·5·1, canary 발동 159번 중 13번). 대조: `+nocanary`(TB가 `can_owns`를 0으로 고정)로 같은 실행을 하면 누락 0, **LPROBE VALID**.
- 빈도: R800 업로드와 재생이 겹치는 phase 4에서 8.77 ms에 5번(초당 약 570번). 보드 빌드의 msx.sv에도 같은 canary가 있다. 소리에 미치는 영향(프레임 하나의 남은 슬롯 빠짐)은 시뮬레이션 출력으로 확인하지 않았다.
- engine3도 같은 브리지를 쓰므로 같은 누락을 겪는다. 고치는 곳은 msx.sv(canary를 없애거나, canary 중 오른 엔진 요청을 붙잡아 두었다가 처리).
- **해결 (2026-10-27, 사용자 결정: canary 제거):** 이 worktree의 `msx.sv`에서 canary를 없앴다. 브리지 입력은 엔진 신호 그대로, `ms_mem_busy = (pcm_state != 0)`, `dbg_env_min = 0`(오버레이는 초록 stub). TB의 canary 카운터와 `+nocanary`도 없앴다. 결과(`/data/_claude/tmp/opl4-scratch/lp/fix/lat.log`): **LPROBE VALID**, 모든 phase에서 상승 = valid, 덮어쓰기 0. 지연 줄은 `+nocanary` 대조와 한 글자도 다르지 않다. 대조: canary가 있던 70f6009의 같은 실행은 INVALID(`lp/can`). 보드 빌드(sdram128 트리)의 msx.sv는 건드리지 않았다.
