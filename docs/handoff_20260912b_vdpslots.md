# 핸드오프 — VDP 커맨드 엔진 타이밍 (2026-09-12)

`docs/handoff_20260912.md`의 "열린 것 2 — ASO 밴드"에서 이어짐.
그 문서가 "CEPROBE 실기 숫자 0건"으로 끝났고, **그 0건을 채웠다.**

**성과: 진단만. 수정 0건. ASO 밴드 그대로.**
워킹트리는 현행과 동일 동작으로 되돌려져 있다(`USE_SLOT_MAP='0'`, 검증 완료).

## 1. 측정 — 이 문서의 본체

조건: G4(SCREEN 5), 디스플레이 ON, 스프라이트 ON, NTSC 192라인, 3.58MHz.
→ 표시 구간 `C_WAIT_TABLE_602`, 수직 보더 `606`.

| 명령 | 우리(TB, 라인) | openMSX | 비 | 실기(D7 정규화) |
|---|---|---|---|---|
| HMMV 256×128 | 807.05 | 722.18 | 1.118 | 1.172 |
| HMMM 256×128 | 1356.09 | 1466.82 | 0.925 | 0.951 |
| LMMV 256×64 | 1708.92 | 1476.01 | 1.158 | 1.161 |
| LMMM 256×64 | 2219.30 | 1744.90 | 1.272 | 1.285 |
| YMMM 256×128 | 1254.92 | 1204.82 | 1.042 | 1.019 |
| LINE ×32 | 1086.60 | 897.35 | 1.211 | 1.247 |
| SRCH ×32 | 348.35 | 670.97 | 0.519 | 0.497 |

**TB·openMSX·실기 3중 일치.** 발산은 −48% ~ +29%, 방향이 제각각이라 단일 계수가 아니다.
보드/TB 비는 평균 +0.8%, 산포 −4.3%~+4.9%, **계통 편향 없음** → TB는 유효한 대리자다.
(그래서 `sim/check_vdpcmd.sh`의 `TOL`을 3%→5%로 올렸다. 3%는 정상 빌드에서도 터진다.)

**엔진 바닥**: `VDPSPEEDMODE='1'`(스로틀 바이패스)로 HMMV = 48.01라인 = **4.0 사이클/바이트**.
목표가 60.9이므로 엔진은 필요분의 15배 빠르다 → **슬롯 공급이 유일한 제약**이고,
"커맨드 엔진 내부 상태기계가 병목"이라는 가설은 죽었다.

## 2. 원인 — 모델의 종류가 다르다

**실칩**(openMSX `doc/internal/vdp-vram-timing/`, 2013년 로직 애널라이저 실측 —
Joost Yervante Damad 님, Alex Wulms 님, Wouter Vermaelen 님): 라인 1368 사이클의 매
VRAM 사이클이 용도별로 **정적 할당**돼 있다. 표시/스프라이트/DRAM 리프레시가 가져가고
**남은 칸만** 커맨드가 쓴다. 불규칙한 이유는 리프레시 의무 + 고정 길이 트랜잭션
(full read 6 cycle, 연속 주소는 페이지모드 버스트) + 2뱅크 병렬.

**우리**(`vdp_wait_control.vhd`): 위상 누산기로 **평균 레이트**만 만든다.
```vhdl
FF_WAIT_CNT <= ('0' & FF_WAIT_CNT(14 DOWNTO 0)) + C_WAIT_TABLE_xxx( VDP_COMMAND );
ACTIVE      <= FF_WAIT_CNT(15) OR VDPSPEEDMODE;
```
값이 클수록 빠르다. 표 간 값 비교는 무의미하다(`DRIVE` 틱 빈도가 위상마다 달라서
각 표가 그 위상의 분자로 따로 보정돼 있다).

**총 소요시간은 평균 레이트로도 맞출 수 있다.** HMMM이 8% 어긋난 건 모델 한계가 아니라
덜 맞춰놔서다 — 602 주석 본인이 "the blank-phase rate stays at 12% slower than real"이라
적어놨다. 일곱 칸 중 HMMM 하나만 보정됐다.

**못 맞추는 것은 라인 안에서의 위치다.** 602 주석에 전례가 있다: "a constant per-frame rate
matched totals but drew a moving row of ghost dots where the front trailed the beam".
ASO 밴드가 래스터 분할 문제라면 정확히 이 층이다.

### 격자가 안 맞는다 (구조적 장벽)

실칩 슬롯은 **전부 짝수 사이클**(2사이클 격자). 우리 중재기는 `H_CNT ≡ 3 (mod 4)`
한 잔여류에서만 배정한다(`DOTSTATE="10"`, 라인당 342회). 전역 오프셋은 하나뿐이라
어느 값을 골라도 한 모드만 맞는다(26/88 ~ 153/154).
→ **커맨드에 2사이클 격자를 줘야 한다.** 홀수 오프셋이면 세 모드 100% 덮인다.

## 3. 정렬 (계산 완료, 교차 검증됨)

```
openMSX 표시 시작 258   (V9938 Technical Data Book: Display cycle [258-1282) = 1024)
우리 표시 시작    219   (vdp_ssg.vhd:294 로드 H_CNT=186 → vdp.vhd:1308 PREWINDOW_X)
오프셋 = 39,  our_H = (openmsx_p - 39) mod 1368
자체 검증: 우리 표시창 [219..1242] = 정확히 1024 사이클
```

| 표 | n | `H≡1` (우리 미사용, `DOTSTATE"01"`) | `H≡3` | 표시창 안 충돌 |
|---|---|---|---|---|
| ScreenOff | 154 | 153 | 1 | **0** |
| **SpritesOn** | **31** | **28** | 3 | **0** |
| SpritesOff | 88 | 26 | 62 | 31~32 |

**스프라이트 ON·표시 OFF에서 충돌 0** → 표시 페치를 건드릴 필요 없다.
**SpritesOff만 31개 충돌**, EDS 한 버킷에 집중. 우리 비트맵 페치가 8도트당 5칸을
예약하는데 G4는 16비트 접근 2회면 충분하다 = **과다 예약**. 별건이고 국소 수정이다.

## 4. 시도한 것과 그 결과 — **`"01"` 2차 슬롯은 한 번도 작동하지 않았다**

`vdp.vhd`에 `DOTSTATE="01"` 2차 접근 기회를 추가하고 슬롯맵으로 게이팅했다.
`DATACHECK`(HMMM 복사 후 8192바이트 대조) + 쓰기 카운터로 재면:

| 빌드 | 전체 쓰기 | 목적지 | |
|---|---|---|---|
| 구 경로 `USE_SLOT_MAP='0'` | 32768 (=16384회) | 16384 | 정상 |
| 신 경로 (양쪽 승인) | 1414 | 886 | 4.3% |
| 단일 창구 (`"10"`→DRAW) | **0** | 0 | 데드락 |
| 단일 창구 (`"10"`→VDPS) | **0** | 0 | |
| 위 + 델타 0 (ACTIVE 상시 1) | **0** | 0 | |
| 위 + G4/G5 가드 제거 | **0** | 0 | |

**`"10"` 분기가 실전송을 안 주는 순간 쓰기가 0이 된다.** 886회는 전부 `"10"` 산물이고,
`"01"` 분기는 조건을 아무리 열어도 걸리지 않는다.
→ **슬롯맵은 실질 적용된 적이 없다.** 이 과정에서 기록된 262.34 / 802.76 / 778.76은
**전부 무효 수치**다. "11% 미달"도 "XFER 수정으로 3% 개선"도 의미 없는 숫자였다.

**확정**: `VDPS`는 중립이 아니라 **엔진의 클럭 인에이블**이다. 빼면 엔진이 요청을 못 올려
아무것도 시작되지 않는다(쓰기 0 실측).

### ★다음 사람이 먼저 할 일

**`vdp_command.vhd`의 REQ/ACK 의미론을 읽어라.** `VDPS`(건너뜀)를 받은 엔진이 요청을
유지하는지 내리는지, `DRIVE` 한 번에 몇 단계 전진하는지. 이걸 모르면 `"01"` 분기를
못 살린다. 이 모듈은 DOTSTATE 참조가 0개라 구조적으로는 독립이지만, REQ/ACK 프로토콜에
암묵적 타이밍 가정이 있는 것으로 보인다.

**조건만 바꿔가며 시뮬을 돌리지 마라.** 2026-09-12에 그 방식으로 여섯 판(판당 3~25분)을
태우고 아무것도 못 얻었다. 코드 200줄 읽는 쪽이 훨씬 빨랐다.

| | |
|---|---|
| `tools/vdpprobe/cmdcmp.s` → `CMDCMP.COM/.DSK` | 7명령 프로브. 보드와 openMSX에서 **같은 바이너리**로 돈다. 빌드 `bash tools/vdpprobe/build_cmdcmp.sh`. 보드 배포됨 |
| `rtl/video/VDP/sim/tb_vdpcmd7.vhd` | GHDL TB. 제네릭 `CMDSEL`(0~6 단일 명령) / `BOARDREGS` / `DATACHECK` |

| `sim/check_vdpcmd.sh` | 회귀 관문. 7행 대조, `TOL`(기본 5%) 밖이면 exit 1 |
| `sim/run_vdpcmd_gofigure.sh` | 구 `tb_vdpcmd.vhd` 러너 (GoFigure `CE_at_FH188`용) |
| `rtl/video/VDP/vdp_slot_pack.vhd` | 실측 슬롯맵 1368×3bit. `tools/gen_vdp_slots.py`로 재생성 |
| `rtl/video/VDP/vdp_access_slots.vhd` | 슬롯맵 게이팅 모듈 (미작동, 위 4절 참조) |

**GHDL**: AUR `ghdl` 6.0.0 (mcode). 플래그·순서는 `sim/run_vdpcmd7.sh`에 있다 —
`--std=93c -fsynopsys -fexplicit -frelaxed-rules`, `vdp_package.vhd` 선행,
`rtl/peripheral/ram.vhd` 포함, **mcode는 실행파일을 안 만드니 `-r`로 실행**,
`--ieee-asserts=disable`.

**openMSX 절대 기준 뜨는 법**: `debug write "VDP regs" 46 …`으로는 커맨드가 안 뜬다
(R#32~46은 openMSX에서 `VDPCmdEngine` 안에 있어 CE가 0으로 유지). I/O 경로는
`CMDCMP.COM`이 타게 두고 **시간만 Tcl 브레이크포인트로** 잰다:
```tcl
debug set_bp <wait_ce>       {} {set ::t0 [machine_info time]}
debug set_bp <call 다음주소>  {} {set ::acc [expr {$::acc + [machine_info time] - $::t0}]}
# 라인 수 = acc / (1368.0/21477270.0)      NTSC 1라인 = 63.695us
```
주소는 빌드마다 바뀌니 `sdasz80 -l`의 `.lst`에서 뜬다(`offset + 0x100`).

## 6. 함정

1. **BDOS는 인터럽트를 켠 채 돌아온다.** `rdst`가 R#15를 마지막 읽은 레지스터에 남기는데
   BIOS ISR은 `R#15=0`을 가정하고 S#0을 읽어 F를 지운다. R#15=2면 F가 안 지워져
   **ISR 무한 재진입**. 배너 `puts` 직후 `di` 필수.
2. **SRCH는 데이터 의존.** 단독 6.85라인 vs 순차 348.35라인 — 첫 매치에서 멈춘다.
   HMMV가 y=128을 먼저 채워야 한다.
3. **S#2의 VR은 bit6이다. bit5는 HR.** bit5를 읽고도 그럴듯한 숫자가 나온다.
4. **openMSX Tcl `puts`는 stdout이 아니라 openMSX 콘솔로 간다.** 파일로 쓸 것.
5. **화면 텍스트를 스샷에서 눈으로 읽지 말 것.** `debug read_block VRAM`.
   네임 테이블 주소가 모드마다 다르다 — SCREEN 1은 `0x1800`, TEXT2는 `0x0000`.
6. **머신팩에 따라 DOS 화면 모드가 다르다.** `CA` 행이 `011D`면 SCREEN 1/29,
   `0050`이면 TEXT2/80. 비교하려면 양쪽을 맞출 것.
7. **하네스가 추적하는 백그라운드 작업은 수명이 하네스에 묶인다.** `SIGSTOP`을 쏘면
   종료로 보고 회수한다(22분치 시뮬 손실). 길게 도는 시뮬은
   `setsid nohup ... &` 로 분리하고, 우선순위는 `renice`로.
8. **`DATACHECK`에 자명 통과 경로가 있다 (미수리).** 원본·목적지를 비교하는데 **둘 다
   안 쓰였으면 `0xA5`끼리 일치해 통과**한다. "264 불일치"가 실제로는 886/16384였던 것이
   쓰기 카운터를 붙이고서야 드러났다. 고칠 것: 원본을 미초기화값과 다른 패턴으로 채운 뒤
   **원본 자체를 기대값과 대조**하고, 쓰기 수를 항상 같이 보고.
   `PRAMWE_N`이 2사이클 유지되므로 카운트는 2배로 나온다.

## 7. 닫힌 가설 (되살리지 말 것)

| | 왜 |
|---|---|
| 엔진이 CPU에 페이싱된다 | `C1`이 클럭에 비례, 두 빌드 재현 |
| G4에서 F 플래그가 샌다 | **openMSX도 똑같이 샌다** = 실칩 거동 |
| 화면 모드/스프라이트 페치가 17%의 원인 | TEXT2 1448 vs SCREEN1 1466 = 1.2% |
| `R#2/R#5/R#6`가 원인 | 스로틀 표 선택 분기에 안 들어감(`R#1/R#8/R#9`만) |
| 보드↔시뮬 5%p 계통오차 | HMMV 한 표본의 산포. `D7` 실측으로 폐기 |
| 커맨드 엔진 상태기계가 병목 | 엔진 바닥 4.0 사이클/바이트 (필요분의 1/15) |
| FH 라인 인터럽트 / 터보 VDP 페이서 (ASO) | 앞 세션 |

## 8. 아키텍처 판정 (포크 평가, 리포 증거로 교차 확인)

- **중추 재설계 가치 없음.** 이식할 검증된 외부 V9938 RTL이 **존재하지 않는다**
  (OCM·MiSTer MSX 계열이 전부 같은 ESE-VDP 계보, openMSX는 소프트웨어).
- **B(표시/스프라이트까지 슬롯맵 위로) 보류.** `vdp_command.vhd`는 도트위상 참조 0개라
  절단면이 깨끗한데, 모드 모듈은 95회(g4567 35 / sprite 36 / g123m 14 / text12 10)
  박혀 있다 = 픽셀 파이프라인 5개 재타이밍. 그리고 표시 페치 타이밍은 **사용자가 보는
  픽셀을 바꾸지 않는다**. 발동 조건("표시 중 칩 슬롯의 >20%를 우리 표시 페치가 점유")은
  실측 0%로 꺼졌다.
- **A(커맨드 승인 경로만 치환) 유지 → 그다음 D(T80s 21.48MHz).** D를 A와 병행하지 말 것
  — 검증 병목(보드·사용자)이 같아서 실기 회귀 시 원인 구분이 불가능하다.
- 1년 rtl/ 커밋 226건 중 **VDP는 8건**인데 조사 세션은 최다 = 커밋당 디버깅 비용이
  극단적으로 높은 서브시스템. 모델 없이 증상만 쫓은 결과다.
