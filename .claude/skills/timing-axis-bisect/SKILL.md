# 타이밍 실패 축 가르기

증상이 클럭에 따라 달라지면 "빠르게/느리게"가 아니라 **어느 축이 원인인지**부터 가른다.
축은 보통 셋이다.

1. **총 처리량** — CPU 클럭 (`z80_freq` / `r800_freq`)
2. **I/O 간격** — 같은 코드 블록 안의 연속 VDP 쓰기 사이 시간
3. **게임 자신의 대기 상수** — 코드에 박힌 지연 루프 값

## 방법: 세이브스테이트 + 구간 한정 클럭

축 2를 축 1과 분리하는 것이 핵심이다. 브레이크포인트로 **블록 진입/이탈 때만** 클럭을
바꾸면, 블록 밖 코드 속도는 그대로 두고 블록 안 쓰기 간격만 바뀐다.

```tcl
debug set_bp $BLOCK_START {} { set ::z80_freq 2080000 }   ; # 느리게 = 간격 넓게
debug set_bp $BLOCK_END   {} { set ::z80_freq 21480000 }  ; # 원래대로
```

축 3은 그 상수를 `poke`로 스윕한다(1단위가 몇 라인인지 먼저 환산).

## 판정은 화면으로, 단 실패 모드를 전부 덮게

색상 다양성(쓰레기)만 보면 **검게 비는 실패**를 놓친다. `omsxprobe.py bands`의
**상·하단 빈 줄 0/0**을 기준으로 삼는다.

## 워크드 예제 — ASO 상하 밴드 (20260920 해결)

- 구조: 패널 리포인트는 **라인 인터럽트라 래스터 고정**(전 클럭에서 라인 231~237).
  속도 의존은 **플레이필드 복귀 한 점**뿐 → 1차원 문제.
- 축 1(클럭)만 흔들면: Z80 3.58~21.48MHz 전 구간에서 실패. 21.48MHz에서 착지 라인이
  실기 R800(28.7라인)과 같아져도 **여전히 깨짐** → 축 1이 원인이 아님.
- 축 2(간격)를 분리하니 뒤집힘:

  | 베이스 10.74MHz 고정, 블록 간격만 | 결과 |
  |---|---|
  | 2 µs / 4 µs | 깨짐 |
  | **6 µs 이상** | **정상(0/0)** |

  착지 라인은 25.8→27.2로 3줄밖에 안 움직이는데 판정이 뒤집힘 = **간격이 인과 변수**.
- 단, **필요 간격은 블록 밖 코드 속도에 비례**한다: 10.74MHz는 ≥6 µs, 21.48MHz는
  8 µs로도 부족하고 ~10 µs에서 넘어감. 실기 R800은 8.66 µs.
- 따라서 코어 수정은 "실기 값 8.66 µs를 넣는다"로 끝이 아니라 **가장 빠른 터보 단수에서
  화면 0/0을 확인**해야 한다.

## 함께 재둘 것

- 리포인트→복귀 경과 라인(µs를 63.7 µs로 나눔) — 진척도 지표로 바로 쓸 수 있다
- 블록 내 레지스터별 착지 시점(쓰기 간격 × 순번) — 어느 레지스터가 데드라인을 넘는지
- 실패의 **기울기**: 1라인 늦을 때마다 쓰레기 1줄 식으로 선형이면 데드라인 역산이 된다
